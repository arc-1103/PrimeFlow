## 1. H0–1 — Interface Freeze (all 4 people, collaborative, not serial)

### Why this is its own section and not "P1's job"
If one person writes `app/schemas.py` alone while three people wait, you've turned a
24-hour parallel plan into a 23-hour parallel plan with a 1-hour bottleneck at the front —
except in practice it's worse, because whoever writes it alone will bias the schema toward
their own track's needs and the other three will discover mismatches at integration time
(H7–11), which is exactly the highest-risk window per `PHASE_0_PLAN.md` §5.

### How to actually run it (45 min draft + 15 min sync)
Each person drafts **only their own track's piece** of the shared contract, in parallel:

| Person | Drafts | Goes into |
|---|---|---|
| P1 | `Chunk`, `RetrievalResult` schemas; `Retriever` abstract interface (method signature only, no implementation) | `app/schemas.py`, `app/retrieval/base.py` |
| P2 | `ControllerDecision` schema (`WAIT` / `RETRIEVE` / `NO_RETRIEVAL` + reason string); `SubQuery` schema | `app/schemas.py` |
| P3 | `AnswerVersion` schema, `Claim` schema, `Session` schema | `app/schemas.py`, `app/session/models.py` |
| P4 | `TelemetryEvent` schema (must cover every event type in `CHALLENGE_BREAKDOWN.md` §B.10 / G6); WebSocket/SSE message contract for the frontend | `app/telemetry/schema.py`, a short `docs/WS_CONTRACT.md` or a section in `docs/ARCHITECTURE.md` |

Then: **15-minute sync, all 4 on a call, screen-share `app/schemas.py`.** Merge the four
drafts into one file, resolve naming collisions, and — this is the important part — **lock
it.** After this sync, changing a shared schema requires grepping for every consumer across
`app/` and `tests/` first (`AGENTS.md` §4) and a heads-up in chat, not a silent edit.

Also in this window (can run alongside the drafting, doesn't need all 4):
- Repo skeleton, `docker-compose.yml`, `Dockerfile`, `pyproject.toml` — **default owner: P1**
  (they need it working first, for `scripts/ingest.py`), but anyone can push the initial
  commit.
- `.env.example` — see the companion `ENV_VARS.md` / `.env.example` already produced.
- `docs/ARCHITECTURE.md` skeleton — **default owner: P4** (they'll be writing the WS
  contract into it anyway), filled in by each track owner as their module lands.

**Stop condition for this phase:** `app/schemas.py`, `app/retrieval/base.py`, and the WS/SSE
contract are committed, and all four people have read the merged version. Nobody writes
implementation code before this is done.

## 2. P1 — Ingestion + Retrieval

### Mission
Turn the raw corpus into something searchable, and make hybrid search actually work. This
is the track everyone else eventually swaps their mocks for — treat "real, working
retrieval by H11" as a hard personal deadline, not a soft target.

### Files owned
```
scripts/ingest.py
app/retrieval/base.py       (drafted H0-1, implemented here)
app/retrieval/dense.py
app/retrieval/sparse.py
app/fusion/rrf.py
app/fusion/rerank.py
app/fusion/dedupe.py
corpus/, data/, indexes/    (pipeline artifacts — regenerated by ingest.py, never hand-edited)
docker-compose.yml, Dockerfile   (default owner, H0-1 only — contributions from others as they add deps)
```

### Detailed responsibilities
- **Ingestion** (`scripts/ingest.py`): parse corpus with **PyMuPDF / python-docx** (per
  `AGENTS.md` §3 — do not write a custom parser). Deterministic chunking is one of the two
  places custom logic is expected (`AGENTS.md` §3) — build the sentence-aware chunker
  carefully, it's graded indirectly via G4 (every claim needs to trace to a real chunk).
- **Dense retrieval** (`dense.py`): `sentence-transformers` embeddings → **FAISS** index.
  No custom ANN index, no Qdrant.
- **Sparse retrieval** (`sparse.py`): `rank_bm25`. No custom TF-IDF/BM25 implementation.
- **Fusion** (`rrf.py`): standard Reciprocal Rank Fusion formula — not a bespoke scoring
  heuristic. `rerank.py`: RRF order is sufficient; a CrossEncoder pass is optional if ahead
  of schedule (see Stretch Goals).
- **Dedupe** (`dedupe.py`): dedupe fused results by `chunk_id`.

### Hour-by-hour (from `PHASE_0_PLAN.md` §3, your rows)
| Window | Task | Stop condition |
|---|---|---|
| H0–1 | Draft `Chunk`/`Retriever` schema in the freeze sync; scaffold `docker-compose.yml` | Schemas merged and locked |
| H1–4 | Parser, chunker, embeddings, BM25, FAISS build | A known query retrieves the correct doc |
| H4–7 | Harden ingestion, start fusion/rerank | — |
| H7–11 | Fusion, rerank, dedupe; **integrate with P2's decomposed sub-queries** (parallel routing) | Compound query → multiple merged, deduped searches |

### Dependencies
- **In:** Nothing blocks you at H1 — you test against the corpus directly. At H7–11 you
  need P2's `SubQuery` output shape (frozen at H1, so this should be a non-event).
- **Out:** P2 needs your `Retriever` interface signature (not implementation) by end of
  H0–1 to build Track B against mocks. P3 needs your **real, working retrieval by ~H11**
  for delta queries and citation validation — this is the integration point that most puts
  the rest of the team at risk if it slips.

### Graded on
G1 (your Docker/reproducibility work), G3 (fusion quality feeds multi-intent scoring), G4
(citation grounding is only as good as your chunk IDs being real and correctly attributed).

### Risk & mitigation
Medium risk on its own, but **high blast radius** — if this slips, P3's H11–14 work and
P4's H17+ real-event telemetry both slip with it. Mitigation: get a *minimal* dense+sparse
path working end-to-end by H4 even if crude, then spend H4–11 improving it, rather than
polishing dense retrieval alone until H7.

### Tests owned
`tests/test_retrieval.py`

### Stretch goals (only if ahead by H11)
- CrossEncoder neural reranker (optional per `CHALLENGE_BREAKDOWN.md` §I — cut-order item
  #2 in `PHASE_0_PLAN.md` §7 if anyone runs short elsewhere).

### Cut first if behind (per §7 cut order)
Don't add the CrossEncoder. Don't touch Postgres/pgvector — that's not even on your list,
it should never be started (§7 item #6).

## 3. P2 — Streaming + Controller + Decomposition

### Mission
Decide, per transcript chunk, whether to search yet — this is called out in
`PHASE_0_PLAN.md` §5 as risk #1, the single hardest-to-get-right piece, and it gates
everything downstream. Then, once RETRIEVE fires, split compound utterances into clean
sub-queries.

> **Note on scope:** the source docs group "Decomposer, parallel retrieval, fusion,
> rerank, dedupe" into one H7–11 deliverable (`PHASE_0_PLAN.md` §3) but never say who owns
> the decomposer itself. It's assigned here, not to P1, because: (a) decomposition consumes
> the controller's RETRIEVE decision and the live transcript context directly — same
> mental model as stability detection; (b) your controller work has its own stop condition
> by H7 ("retrieval visibly starts before utterance ends"), which frees you to start
> decomposition exactly when it needs to start, in parallel with P1's continued fusion
> work — rather than loading an already-heavy Track A with a 7th and 8th file.

### Files owned
```
app/streaming/simulator.py
app/streaming/events.py
app/controller/stability.py
app/controller/llm_fallback.py      (optional — see cut list)
app/decomposition/decomposer.py
```

### Detailed responsibilities
- **Simulator** (`simulator.py`): feeds timestamped transcript chunks as an event stream —
  this is your test harness for everything else, build it first.
- **Controller** (`stability.py`): rule-based heuristics only, per `CHALLENGE_BREAKDOWN.md`
  §J — **do not build a trained classifier**. Combine: entity/slot completeness,
  sentence-boundary + minimum-token heuristics, a formatting-only-instruction
  keyword/regex check (for presentation-suppression, §B.7 / Example 3). Every decision
  must log a reason string (feeds G6).
- **LLM fallback** (`llm_fallback.py`, optional): one LLM call for genuinely ambiguous
  cases only. Per `PHASE_0_PLAN.md` §5, this must not become the single point of failure —
  pure heuristics should already clear G2's 80% target on well-behaved prompts.
- **Decomposer** (`decomposer.py`): split on clear compound markers — conjunctions,
  multiple question words, multiple distinct entities. **Same-query fallback on low
  confidence** (`PHASE_0_PLAN.md` §6) — don't force a split that isn't there. Watch for
  pitfall #5 in `CHALLENGE_BREAKDOWN.md` §G: over-fragmenting into near-duplicate
  sub-queries pollutes the reranker and burns token budget.

### Hour-by-hour
| Window | Task | Stop condition |
|---|---|---|
| H0–1 | Draft `ControllerDecision`/`SubQuery` schema in the freeze sync | Schemas merged and locked |
| H1–4 | Simulator + event stream, start heuristics | — |
| H4–7 | WAIT/RETRIEVE/NO_RETRIEVAL heuristics against mocked `Retriever` | **Retrieval visibly starts before the utterance ends** |
| H7–11 | Decomposer: compound-marker splitting + confidence fallback; wire real sub-queries into P1's parallel retrieval | Compound query → multiple merged searches |

### Dependencies
- **In:** Only needs P1's `Retriever` *interface* (frozen H0–1), not the implementation —
  build and test against a mock retriever that returns canned results. This is explicitly
  why Track B can start immediately per `PHASE_0_PLAN.md` §4.
- **Out:** P3's synthesis needs your `ControllerDecision` + decomposed `SubQuery` list to
  know what was searched for and why (feeds the answer's provenance). P1 needs your
  `SubQuery` output shape for parallel routing at H7–11.

### Graded on
**G2 directly** (early retrieval, ≥80% of eligible queries, without excessive false
triggers), **G3 directly** (≥70% of compound queries correctly split into ≥2 sub-intents).

### Risk & mitigation
**Highest individual risk on the team.** Per `PHASE_0_PLAN.md` §5: too aggressive → noisy
premature searches (pitfall #1 in `CHALLENGE_BREAKDOWN.md` §G); too conservative → misses
the "before utterance ends" target. Mitigation: start generous (tuned against the spec's
own Example 1), keep the LLM fallback strictly for ambiguous cases so a heuristic bug
doesn't cascade.

### Tests owned
`tests/test_controller.py`, `tests/test_decomposition.py`

### Cut first if behind (per §7 cut order)
LLM-fallback in the controller is cut-order item #5 — pure heuristics can still hit G2's
target on well-behaved test prompts. Cut this before you cut anything in the core
stability heuristics.

## 4. P3 — Session + Synthesis + Grounding

### Mission
This is the answer itself — session continuity, late-constraint patching without a full
restart, and making sure nothing gets stated as fact without a real citation. Per
`PHASE_0_PLAN.md` §5, this is risk #2 and it fails G4 and G5 *together* if it's wrong.

### Files owned
```
app/session/store.py
app/session/models.py        (AnswerVersion, Claim, Session — drafted H0-1, implemented here)
app/synthesis/generator.py
app/synthesis/delta.py
app/grounding/citation_validator.py
app/grounding/uncertainty.py
```

### Detailed responsibilities
- **Session store** (`store.py`): **SQLite**, keyed strictly by `session_id`. No
  Postgres/pgvector. Must pass the cross-session isolation unit tests — this is a hard
  constraint (`AGENTS.md` §2), not a nice-to-have.
- **Session models** (`models.py`): `AnswerVersion`, `Claim`, `Session`. **Design this
  before writing any retrieval-consuming code** — `PHASE_0_PLAN.md` §5 calls this out
  explicitly as the mitigation for risk #2. It's why this schema is part of the H0–1
  freeze, not an H11 afterthought.
- **Synthesis** (`generator.py`): LLM call via the OpenAI-compatible client abstraction
  (`AGENTS.md` §3) — never hard-code a single-vendor SDK call scattered through the code.
  Session-aware: must incorporate established facts from prior turns.
- **Delta engine** (`delta.py`): the second place custom logic is expected and correct
  (`AGENTS.md` §3). On a late-arriving constraint, retrieve *only* the delta (via P1's
  retriever, scoped by P2's targeted sub-query), patch the existing `AnswerVersion` into a
  new version, **preserve everything still valid**. Never trigger a full pipeline re-run —
  this is graded (G5) and the hard constraint explicitly warns against regressing it while
  touching this code (`AGENTS.md` §2).
- **Citation validator** (`citation_validator.py`): every `[Doc_ID §Section]` tag must
  reference a chunk ID that actually exists in `data/chunks.jsonl` **and actually supports
  the claim** — string/keyword overlap check or an LLM-graded check. Refuse ungrounded
  claims rather than let them through.
- **Uncertainty detector** (`uncertainty.py`): when corpus evidence is insufficient for a
  sub-intent, emit an explicit uncertainty string. Never guess, never invent a doc ID
  (`AGENTS.md` §2 — this is a hard constraint, treat a fabricated ID as a build-breaking
  bug, not a quality issue).

### Hour-by-hour
| Window | Task | Stop condition |
|---|---|---|
| H0–1 | Draft `AnswerVersion`/`Claim`/`Session` schema in the freeze sync | Schemas merged and locked |
| H1–7 | Build session store + synthesis against **mocked retrieval results** | — |
| H7–11 | Continue synthesis; start delta engine design | — |
| H11–14 | Session store, answer versions, delta engine against **P1's real retrieval** | Late constraint updates the answer, no restart |
| H14–17 | Citation validator, uncertainty detector against **real chunk IDs from P1's indexes** | Unsupported claims explicitly flagged |

### Dependencies
- **In:** Can build against mocks H1–7 (per `PHASE_0_PLAN.md` §4, Track C is explicitly
  designed to be testable this way). **Needs P1's real retrieval working by ~H11** for the
  delta engine, and **real chunk IDs by ~H14** for citation validation to mean anything.
  Needs P2's decomposed sub-queries to know what was actually asked.
- **Out:** P4's telemetry needs your `AnswerVersion` lineage (version history) to satisfy
  G6's "version lineage" trace requirement. The demo and eval report need your citation
  validator's pass/fail output directly (G4 is measured off this).

### Graded on
**G4 directly** (≥85% citation support, zero fabricated doc IDs), **G5 directly**
(verified continuity — targeted retrieval + answer delta, never full re-search).

### Risk & mitigation
**Highest risk on the team, tied with P2**, and the more state-heavy of the two — per
`PHASE_0_PLAN.md` §5 this is "the most state-heavy, easiest-to-get-subtly-wrong part of
the system." Mitigation is structural, not just careful coding: the data model
(`AnswerVersion`/`Claim`) must exist before H1 is over, which is why it's in the freeze
sync rather than something you design alone at H11 under time pressure.

### Tests owned
`tests/test_session_refinement.py`, `tests/test_grounding.py`

### Cut first if behind
Nothing in this track is on the optional list in `CHALLENGE_BREAKDOWN.md` §I — G4 and G5
are both mandatory, gate-critical, cannot be cut. If you're behind, the fix is to ask P1
for an earlier real-retrieval handoff (even partial), not to cut scope here.

## 5. P4 — Telemetry + Evaluation + Frontend

### Mission
Two low-coupling, high-leverage tracks bundled onto one person because both are
contract-consumers, not contract-producers, and once the H0–1 schemas exist, they touch
almost entirely disjoint files from each other. You are also, functionally, the person who
proves the other three people's work is correct — start early, don't wait.

### Files owned
```
app/telemetry/logger.py
app/telemetry/schema.py        (drafted H0-1, implemented here)
app/evaluation/gates.py
app/evaluation/fixtures/
scripts/run_eval.py
frontend/index.html
tests/test_gates.py
docs/ARCHITECTURE.md           (skeleton owner — filled in by all as modules land)
docs/HACKATHON_STATUS.md       (keep in sync with every run_eval.py output — AGENTS.md §6)
```

### Detailed responsibilities
- **Telemetry schema** (`schema.py`): must cover every event type the spec lists —
  timestamps, retrieval trigger events, decomposition events, answer version updates,
  citation checks, inference cost estimates (`CHALLENGE_BREAKDOWN.md` §H.5). This has to
  exist at H1, not H17 — see the note below on why the 24h table's placement of this is
  misleading.
- **Logger** (`logger.py`): Python `logging` + JSON formatter (`AGENTS.md` §3) — no custom
  telemetry framework. Build it as a small utility each other track imports and calls
  directly — **don't take on editing P1/P2/P3's files yourself to add logging calls**, that
  serializes H17–19 through you and kills parallelism right when everyone's converging.
- **Eval gates** (`gates.py`, `run_eval.py`): G1–G6 automated checks, printing a results
  table. Scaffold against **mock events from H1** — `PHASE_0_PLAN.md` §4 explicitly says
  Track D "can be scaffolded from day one against mock events, then pointed at the real
  pipeline once it exists." Don't wait for H17.
- **Frontend** (`index.html`): plain HTML/CSS/vanilla JS over the WS/SSE contract you
  froze at H1 (`AGENTS.md` §3 — no React/Vite for a single demo page). Live transcript
  feed, controller decision badge, sub-query list, retrieved sources, streamed answer,
  citations, telemetry/latency strip (`CHALLENGE_BREAKDOWN.md` §J). No auth, no
  multi-page app.

### A correction to the source docs' own timeline
`PHASE_0_PLAN.md` §3 places "Telemetry" at H17–19, but §4 says Track D scaffolds "from day
one against mock events." Follow §4. If you wait for H17 per the table, you'll have ~2
hours to build a 100%-trace-coverage system against three other people's real code
simultaneously finishing — that's the version of this plan most likely to fail G6.

### Hour-by-hour (corrected)
| Window | Task | Stop condition |
|---|---|---|
| H0–1 | Draft `TelemetryEvent` schema + WS/SSE contract in the freeze sync | Schemas merged and locked |
| H1–7 | Scaffold `gates.py`/`run_eval.py` against mock events; start `logger.py` utility | Eval harness runs against fixtures, all 6 gates have executable (if failing) tests |

### Dependencies
- **In:** Needs nothing but the H0–1 schema freeze to start meaningfully. This is

- **Out:** Nobody is blocked waiting on you until H19–21, when your `run_eval.py` output

### Graded on
G1 (your `docker compose up` reproducibility check, jointly with P1's infra),

### Risk & mitigation
Lower individual technical risk than P2/P3, but **highest schedule risk if you follow the

already built into the corrected schedule above — start H1, not H17.
